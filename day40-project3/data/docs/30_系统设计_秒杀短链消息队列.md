# 系统设计面试题 — 秒杀、短链、消息队列

---

## 一、短链接系统设计

### 核心要求
- 支持每秒百万级请求，短链长度 ≤ 6 位
- 保证 URL 全局唯一性
- 支持水平扩展和高可用

### ID生成方案
- **Snowflake算法**：64位整数（时间戳+机器ID+序列号）
- **Base62编码**：a-z, A-Z, 0-9，6位编码可表示约568亿个URL

### 存储方案
- **Redis Cluster**：热点数据缓存，TTL 1-24小时
- **MySQL分库分表**：按短链hash分表存储映射关系
- **本地缓存Caffeine**：兜底

### 重定向
- **301**：永久重定向，浏览器缓存，直接跳转
- **302**：临时重定向，每次都请求短链服务（可统计数据）

### 高可用
- Redis哨兵/集群模式
- Nginx负载均衡
- 多机房部署

## 二、秒杀系统设计

### 核心挑战
- 支持 10万+ QPS
- 避免超卖/少卖
- 全链路削峰填谷

### 架构设计
```
客户端 → 验证码 → API网关(令牌桶限流) → Redis预减库存(Lua原子) → Kafka异步下单 → 数据库最终落库
```

### 核心问题与方案

| 问题 | 解决方案 |
|------|----------|
| **超卖** | Redis Lua脚本原子扣减 + MySQL乐观锁兜底 |
| **刷单** | IP限流 + 验证码 + 用户维度分布式锁 |
| **缓存击穿** | 热点数据预加载 + 互斥锁 |
| **数据库压力** | 分库分表 + Kafka异步削峰 |
| **重复下单** | MySQL唯一索引 + Redis分布式锁 + 幂等性设计 |

## 三、消息队列

### 如何保证消息不丢失？
- **生产端**：Confirm机制，ACK确认
- **Broker端**：持久化到磁盘，多副本
- **消费端**：手动ACK，处理完再确认

### 消息重复消费怎么处理？
- 业务幂等设计：唯一ID + 状态机校验
- 数据库唯一索引
- Redis记录已处理的消息ID

### 消息积压怎么办？
- 临时扩容消费者实例
- 增加分区
- 降级非核心业务
- 批量消费

### Kafka vs RocketMQ

| 维度 | Kafka | RocketMQ |
|------|-------|----------|
| 设计目标 | 高吞吐 | 高可靠 |
| 事务消息 | 不支持 | 支持 |
| 消息过滤 | 客户端过滤 | 服务端过滤 |
| 适用场景 | 日志、大数据 | 金融、交易 |

### 消息顺序性
- 同一Key路由到同一Partition
- 单Partition内有序
- 消费者单线程处理
